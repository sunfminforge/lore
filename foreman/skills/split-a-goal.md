# Splitting a goal

The scheduler starts you on a goal with a brief: the goal, the roles lore has,
the roles drafted in lore's open pull requests, and the split rules.

- Split into as many tasks as the goal needs, and no more: the fewest that keep side-by-side work apart. No rule limits how many; the machines bound how many run at once. A small goal is one task. {#split-into-as-many-tasks-as-the}
- Split by independent artifacts: two tasks that may run side by side change different paths. A coupled design is one task, or tasks in order (`after`). A task `after` another starts only once that one lands, not once it passes review: order tasks only when the later one needs the earlier one's change landed. A task `after` another that changes the same paths could be that task's own work: merge them, or say in its `apart` why they cannot be one (a review that must land first, a different role's work); the split rules refuse one that says none. Ask the same of every two tasks: why not one? {#split-by-independent-artifacts}
- Split only work that can start now. Scope each task only in repos the forge has: a task in a repo the scheduler cannot clone fails before it starts. Check every repo of the split with `git ls-remote <forge>/guild/<repo>.git` first (the `origin` of lore shows the forge); the brief's example repo is an example, not a repo you have. Work that builds on what has not landed (another goal's task: `after` names only tasks of the same split) cannot start either: a constraint telling the worker to wait only parks it and fails the task. Leave such a piece out of the split, a repo to be made (`guild repo new`, on the Hub, not yours to run) or work of another goal, and say on the goal what it waits for and whose move that is; split it once it has landed. {#split-only-work-that-can-start}
- Give each task a `priority` within the goal's: the critical path highest, work that can wait lower. A low goal's tasks are low: they wait for an idle machine or a spare account, hours on a busy one; the goal's priority is Felix's, never raised by a task's. {#give-each-task-a-priority-within}
- Give each task a role lore has, or one drafted in lore. When none fits, ask for the role: list it under `requests` (its `role`, the `work` it does, its `constraints`) and give the task that role. The scheduler opens the role request as a task for the trainer crew; the task waits until the role lands. {#give-each-task-a-role-lore-has}
- While lore has no warden, the split is refused: the trainer drafts it first. {#while-lore-has-no-warden-the}
- Give every acceptance item its check, how it is verified: a `command` and what it must show, which the warden reruns; a `ui` walk-through and what must be seen; or a `link`. An item with none refuses the split. An item that comes true only after the work lands (a tool in forge's index, one that runs by its name once released) is marked `after: landed`, or `after: released`, beside its check: its worker leaves it, the work lands without it, and a follow-up of the task checks it; without the mark the task fails however well it is done. {#give-every-acceptance-item-its}
- A check runs with what its checker is given: its repo, fixtures, its own account. One that needs a credential, an account or a machine no worker, warden or verifier of the task is given (a read-only token for a live service, say) never passes: the task fails or is sent back however good its work, and naming another checker (`by: "warden"`) helps only when that one holds it. Know it from whoever hands credentials out (the steward), asked and answered, never from a suggestion, a role's name or a hope: an assumed holder fails the task in review, and re-splitting it then goes back and forth. Check what can be checked now (on fixtures), and leave what needs the missing credential out of the split, as a piece that cannot start yet: a credential is a person's to make, so say on the goal what it waits for and that it is Felix's or the steward's move. {#a-check-runs-with-what-its}
- A check that needs more than a command the warden can rerun, a UI tried for real or a recording, gets a verification task of its own: after the change alone, its `verifies` naming the items it walks, for a verification role other than the change's (a UI tester; ask for it when none fits, with the capabilities it needs), changing nothing the change changes. It hands in evidence; the warden judges it in the change's review. {#a-check-that-needs-more-than-a}

Write the split to a file and run `guild goal split <goal> <file>`. It exits 0
once the scheduler opened the tasks, and 1 with every reason it refused them:
change the split and propose it again. Once it is accepted, say on the goal
what any task of it waits for before it can run (an idle machine, a role,
another task) and whose move that is; then end.
