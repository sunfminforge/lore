# Splitting a goal

The scheduler starts you on a goal with a brief: the goal, the roles lore has,
the roles drafted in lore's open pull requests, and the split rules.

- Spec the goal before you cut it, short, from the goal and its repos alone, after Matt Pocock's to-spec: nobody is interviewed. The problem and the solution as whoever asked sees them; the decisions it takes (modules, interfaces, contracts, data shapes), in the repo's glossary terms and true to its ADRs; how it is tested, at the highest seam the repo has, with the fewest new ones; and what is out of scope. Say it on the goal. Each task's objective, constraints and acceptance come from it, and what it rules out is in no task. {#spec-before-cutting}
- Question the spec against each repo's ADRs and GLOSSARY (read from its main) before you cut it, in place of Matt Pocock's grill-with-docs, in rounds: first the questions whose prerequisites are settled, each with your recommended answer, then those the answers open, until none is left. Nobody is grilled and Felix is not asked: each question is decided by its recommended answer, which keeps to what the ADRs decided and the terms the glossary defines, and the decision is written into the tasks it bears on, as a constraint or an acceptance item. A fact is looked up in the repo, never put to a worker. Every decision goes into the constraints most of all where nothing else holds it: a fresh repo with no ADRs or glossary yet, or a decision against what the task's role believes (state stored where the role says derived, say), for a worker follows its role where its task is silent. Where the goal asks against an ADR, or uses a term against the glossary's meaning, name the conflict on the goal: the ADR or term, what the goal asks, and how the split decided it. {#question-against-adrs}
- Before you split a self goal (a wait, a refusal or steps repeated across tasks, as Guild measured them), read its evidence per task, not the week's sum: the flow records (`guild flow <goal>` for each goal it names, and for the tasks still waiting the L3 flow table's why over time), each task's issue comments, each run's last stop, the scheduler's log, and the steward's daybook and what it said. The sum is often one task, and over few goals the p90 is their slowest: trace that one wait. A wait naming an account's state (tight, say) is read from that account's own readings in Guild's ledger first, how old the last is and whether its use moved across them, never from the wait's words alone. A counter that never advances or resets before its threshold, many short waits that grow with volume, or a threshold is Guild's code, not a lever; a wait on another task is that task's own review and landing counted again, and sits with them; an approval already given leaves only the step after it. Then find what is done already: the guild fleet's tickets, open and closed, those the steward filed, and any open self goal with the same marker or a role request for the same work, whose role and request you reuse word for word; a cause a running sibling self goal already holds is left to it. Split only the residual: a cause already fixed, or in Guild's code, takes no task, save a stopgap the goal itself offers (one in lore, say); a cause in Guild's code not yet filed goes under the split's `tickets` with its evidence and the source line, found by searching Guild's source for the wait's own words, never as a task whose only work is to file it nor as a file in `guild/tasks`, which takes no pushes and strands the commit; a split of tickets alone, with no task, is accepted, and the goal then waits on its measure; a cause that is Felix's move (a machine, say) is said on the goal. {#self-goal-evidence-first}
- Before you split a tool request, read what its cited tasks' steps really did: it names each step by its first words only, so read their exact commands whole in L3's `steps` table (`guild tool l3-query`), for a repeated step is often a re-run to see what a `tail` cut off, and find the step no released tool does. Look for the tool in forge's main everywhere, released or not, and in its tool index: one that almost covers it is extended, one landed but unreleased is released as it is, and only what neither does is built, said so in the objective. It is one task for the role lore has for CLI tools, scoped to the tool's own paths and the lockfile; a request to fold one tool into another is that one task too, the surviving tool extended and the other's crate deleted: before you split it `git grep` the retired name over forge and lore, and the surviving crate's name over forge's manifests, and scope into that one task, beside both crates and the lockfile, every crate whose help, hints or README name the retired tool and every crate that uses the surviving one as a library; a role in lore that names it is said on the goal, for the trainer crew. Fix the tool's name in the split, for its `after: released` item calls it by that name from a forge checkout, with no fixtures of its own: so it reads live data that no longer changes (a closed pull, a landed task), never an open one, nor a list that is empty today; a tool that writes (a comment, a pull) is called there by its `--dry-run`, which a constraint makes send nothing and read nothing, so it holds on any real <repo>#<n>. The brief of the last tool task that landed is a split the rules accepted: start from it. {#tool-request}
- Split into as many tasks as the goal needs, and no more: the fewest that keep side-by-side work apart. No rule limits how many; the machines bound how many run at once. A small goal is one task. {#fewest-tasks}
- Split by independent artifacts: two tasks that may run side by side change different paths, and each passes the repo's gate on its own: where the gate checks the whole repo at once (every crate of a workspace, say), a fix spread across it lands only whole and is one task, as is a new project on a fresh repo, whose every piece shares its manifest and gate, so run the gate on a clone before you cut. A coupled design is one task, or tasks in order (`after`). A task `after` another starts only once that one lands, not once it passes review: order tasks only for a reason (the later one needs the earlier one's change landed, or changes the same paths or the same role's files); the split rules refuse an `after` with none, such as one role's lore change after another role's that shares no path. Roles taking the same change (one skill adopted by two) are one task, so what they share is written once. A task `after` another that changes the same paths could be that task's own work: merge them, or say in its `apart` why they cannot be one (a review that must land first, a different role's work); the split rules refuse one that says none. Ask the same of every two tasks: why not one? {#split-by-artifacts}
- Cut each task as a tracer bullet, after Matt Pocock's to-tickets: a narrow but whole path through every layer its piece touches (data, logic, interface, tests), which its checks show working on its own, sized to one instance's budget; never one layer left for a later task to wire up. Its blocking edges are its `after`: the tasks whose landed change it needs, and no others; a task with none starts now. A prefactor that makes the slices easy is a task of its own, first, when it is work of its own size; a short one is folded into the task that needs it, for each task put in front of others costs them its whole landing cycle. A wide mechanical change (a rename or retype across a codebase) that no slice can land green is the exception: expand (the new form beside the old), then migrate in batches sized by blast radius, each `after` the expand, then contract (drop the old form) `after` every batch. Say each task's objective as the behaviour it makes work, in the repo's glossary terms, not as files: its scope says where. {#tracer-bullet-tasks}
- Split only work that can start now. Scope each task only in repos the forge has: a task in a repo the scheduler cannot clone fails before it starts. Check every repo of the split with `git ls-remote <forge>/guild/<repo>.git` first (the `origin` of lore shows the forge); the brief's example repo is an example, not a repo you have. Work that builds on another goal's open task (a redraft of the same role in lore, say: `guild status` shows its queue) names it in `after` as `"guild/tasks#<n>"` and starts once it lands; where several queued tasks change the same paths (a tool's crate, say), the last of them, and what each of them bumps (a version) is said as one step above main's at the task's start, never a fixed number; read that task's state first, for one that failed parks yours: where your piece can be built apart, build it apart and leave folding the two for later. An open lore draft on the same role with no task behind it (lore's `refs/pull/*`) is named in the task's constraints. A constraint telling the worker to wait only parks it and fails the task. A piece that needs what no task makes (a repo to be made: `guild repo new`, on the Hub, not yours to run) is left out of the split and said on the goal, with what it waits for and whose move that is; split it once it is there. {#only-work-that-can-start}
- Give each task a `priority` within the goal's: the critical path highest, work that can wait lower. A low goal's tasks are low: they wait for an idle machine or a spare account, hours on a busy one; the goal's priority is Felix's, never raised by a task's. {#task-priority}
- Give each task a role lore has, or one drafted in lore. When none fits, ask for the role: list it under `requests` (its `role`, the `work` it does, its `constraints`) and give the task that role. The scheduler opens the role request as a task for the trainer crew; the task waits until the role lands. {#task-role-or-request}
- While lore has no warden, the split is refused: the trainer drafts it first. {#no-warden-no-split}
- Run each command check before you split on a fresh clone of the repo's main from its origin, never a local checkout, whose main may be stale: one that fails already, for a reason the goal never names, is work its task takes too, said in its constraints. Give every acceptance item its check, how it is verified: a `command` and what it must show, which the warden reruns; a `ui` walk-through and what must be seen; or a `link`. An item with none refuses the split. An item that comes true only after the work lands (a tool in forge's index, one that runs by its name once released) is marked `after: landed`, or `after: released`, beside its check: its worker leaves it, the work lands without it, and a follow-up of the task checks it; without the mark the task fails however well it is done. So is every item waiting on one of Guild's own steps, which no worker takes (the review, a lore upgrade's replay, the landing, a release): mark it `after: landed` (an upgrade lands only once its replay passes) or `after: released`, or drop it, for Guild takes that step anyway. One true only after the session that no step brings (a measure that recovers) is no task's item: the task settles when its session ends, and an item still todo fails it; say it on the goal as what the goal waits for, and whose move it is. {#every-item-a-check}
- A check runs with what its checker is given: its repo, fixtures, its own account, and the programs its role declares in its `role.toml`, in a shell whose PATH may lack them, so a command names where its toolchain installs it (`PATH="$HOME/.cargo/bin:$PATH" cargo …`); a walk that builds what it walks needs a role that declares the toolchain and the driver, for one that declares none runs on a machine without them and fails in minutes: read it before you give the task that role, and ask for one that declares them. One that needs a credential, an account, a program or a machine no worker, warden or verifier of the task is given (a read-only token for a live service, say) never passes: the task fails or is sent back however good its work, and naming another checker (`by: "warden"`) helps only when that one holds it. Know it from whoever hands credentials out (the steward), asked and answered, never from a suggestion, a role's name or a hope: an assumed holder fails the task in review, and re-splitting it then goes back and forth. Check what can be checked now (on fixtures), and leave what needs the missing credential out of the split, as a piece that cannot start yet: a credential is a person's to make, so say on the goal what it waits for and that it is Felix's or the steward's move. {#check-within-what-is-given}
- A check that needs more than a command the warden can rerun, a UI tried for real or a recording, gets a verification task of its own: after the change alone, its `verifies` naming the items it walks, for a verification role other than the change's (a UI tester; ask for it when none fits, with the capabilities it needs), changing nothing the change changes: the change is scoped to its own paths, never the whole repo (`[]`), or the verification's scope falls inside it and the split is refused. It hands in evidence; the warden judges it in the change's review, against the verified item's check, not the verification task's own. So the verification task's acceptance asks for all that check must show, each action and state it names (every screen's main action done, seeded and empty, light and dark), never a lesser record of it (a screenshot per screen): a walk that met its own item but left part of the check unseen sends the change back however good its work. {#verification-task}
- When questioning leaves decisions nothing known now settles (a fact to research, a prototype to react to, work that must be done before a choice can be judged), chart a map of decisions on the goal, after Matt Pocock's wayfinder, in place of cutting the whole goal. Name its destination (the spec, decision or change the goal finds its way to). Split now only what you can state sharply: one decision task per question, each sized to one instance, its item a `link` to where its answer is written (an ADR in the repo where the choice is hard to reverse, surprising without context and a real trade-off; else its task's issue), `after` where one gates another; and the building tasks already clear. What is in scope but too foggy to phrase sharply stays on the goal as not yet specified; what is past the destination, as out of scope; neither is split. {#map-of-decisions}
- Resolve the map one decision at a time: as each decision task lands, say its answer on the goal in one line beside the task (decisions so far), then add the tasks it made specifiable (`replaces: []`), take what it showed past the destination out of scope, and let the rest of the fog wait for the next answer. The map is done when nothing is left to decide; what remains is building, cut as tracer bullets. {#resolve-one-decision-at-a-time}

Write the split to a file and run `guild goal split <goal> <file>`. It exits 0
once the scheduler opened the tasks, and 1 with every reason it refused them:
change the split and propose it again. Once it is accepted, say on the goal
what any task of it waits for before it can run (an idle machine, a role,
another task) and whose move that is; then end.
